# Building and releasing

How the workspace installs, the repository-level steps — generating the documentation, deploying the portal, and cutting a release — and the rules that scripts, CI and dependencies follow.

The engine's own build — the intermediate `lib/`, the bundles, and packaging — is in [`hyperformula/dev-docs/BUILD.md`](../hyperformula/dev-docs/BUILD.md).

## Install

Node version is pinned in the root [`.nvmrc`](../.nvmrc) — 22. It is the only one: the whole repository runs on one Node version, and `nvm` finds it from any subdirectory. The repository uses npm workspaces with a committed `package-lock.json`, so install with `npm ci`, not `npm install`.

```bash
npm ci              # the workspace: hyperformula
npm run docs:install # the portal, which is not a workspace member
```

Root scripts fan out to the packages. `npm run lint` fans out to every workspace that defines it, each with its own configuration; the portal, which installs separately, is linted with `npm run docs:lint`. To run a package's own scripts, work from its directory or pass `--workspace=hyperformula`.

## Generated documentation

| File | Generated by | Rule |
|---|---|---|
| `docs/api/` | `npm run typedoc:build-api` — TypeDoc runs inside `hyperformula/`, where the `tsconfig.json` is, and writes across into the portal | Never edit. Change the JSDoc in `hyperformula/src/`. |
| `docs/guide/built-in-functions.md` | `npm run docs:generate-function-docs`, which runs `docs/script/generate-builtin-functions-doc.ts` against the metadata catalogue | Never edit, never commit. Needs the portal installed. |

The generator lives in `docs/script/` rather than beside the engine build scripts because it uses `@vuepress/shared-utils` for slugs, and that package only resolves inside a full VuePress dependency tree.

Both are git-ignored, and both are regenerated as the first step of `docs:dev` and `docs:build`. `docs:generate-function-docs` is a gate, not a formatter: it fails the build on a missing catalogue entry or a `'Custom'` category. See [`FUNCTION-CATALOGUE.md`](../hyperformula/dev-docs/FUNCTION-CATALOGUE.md).

After `docs:build`, the `build-docs` workflow runs `npm run check:citation-markers`. It fails when a citation marker from a draft document (the patterns are listed in the script) appears in the engine's build output or in `docs/api/` and `docs/guide/`, and when one of those directories is missing or empty.

## Deploying the portal

The portal is served by a Cloudflare Worker, and **deployment is driven by Workers Builds on push, not from a developer's machine**: `master` deploys to production, every other branch uploads a preview version. The commands below exist for debugging that pipeline. The triggers, the Worker name, and the dashboard build settings are in [`docs/README.md`](../docs/README.md#deployment).

| Command | Does |
|---|---|
| `npm run docs:build:cf` | `docs:install`, then the full portal build from an empty output directory. Like `docs:build`, it ends by composing the Worker asset tree through `docs/script/prepare-cf-assets.js` |
| `npm run docs:deploy:cf` | `wrangler deploy` — production |
| `npm run docs:preview:cf` | `wrangler versions upload` — a per-branch preview URL |

Config is [`docs/wrangler.jsonc`](../docs/wrangler.jsonc); the Worker entry point is [`docs/worker/index.js`](../docs/worker/index.js).

## Release and licences

`npm run release` runs `script/release/release.sh`, which releases the engine only. Releasing is maintainer-owned — do not invent steps around it, and do not run it as part of another task.

The `hyperformula-ui` package is released by hand, on its own version line: [`hyperformula-ui/dev-docs/RELEASE.md`](../hyperformula-ui/dev-docs/RELEASE.md).

`npm run check:licenses` asserts that every production dependency carries a permissive licence.

## Scripts and CI

Where each script lives and what calls it is in [`STRUCTURE.md`](STRUCTURE.md#scripts-at-each-level). The release script keeps its own rules in [`script/release/release-README.md`](../script/release/release-README.md).

- **A step runs in the workflow that needs it.** A step only the tests need belongs to the test workflows, not to `lint`.
- **`pre*` and `post*` scripts run the way the scripts are actually called** — by CI, and on a maintainer's machine. npm skips them when `ignore-scripts` is set, which is why `script/release/release.sh` copies the root files itself before `npm publish` instead of trusting `prepack` alone.
- **Generated files are not committed.** They are listed in `.gitignore` and generated before use, like the [generated documentation](#generated-documentation).
- **New npm scripts follow the existing naming:** `group:variant`, as in `test:jest`, `bundle:es` and `verify:typings`, with a `docs:` prefix at the root for the portal's.
- **Checks compute from the real source**, such as actual file hashes or the directory listing, not from a hand-written list ([single source of truth](CODE-STYLE.md#design)).
- **Every step verifies that it did something.** It prints no success message after a no-op, skips nothing silently ([never fail silently](CODE-STYLE.md#style)), and keeps file modes.
- **Sibling commands and code paths are equally robust.** For example, the release script's `code-freeze` checks as much as its `publish`.
- **Diagnostics are accurate.** The error class is the right one, and a message says "tag" or "commit" for the thing it actually found.
- **CI covers new directories.** A new directory is added to the paths and checks of every workflow that should see it.

## Dependencies

- **A new dependency earns its place.** It is needed and maintained. One the published engine depends on is also ESM-friendly and headless — see the engine's [invariants](../hyperformula/dev-docs/ARCHITECTURE.md#invariants) — and its licence passes `check:licenses` ([above](#release-and-licences)).
- **Declare a dependency in the package that uses it.** Never rely on one that arrives transitively or is hoisted from another package's tree; [Workspaces](STRUCTURE.md#workspaces) shows how that breaks. What the published code needs at runtime goes in `dependencies`, the rest in `devDependencies`, and a dependency nothing uses is removed.
- **Fix vulnerabilities in runtime dependencies first.** `.github/workflows/audit.yml` runs `npm run audit` (`npm audit --omit=dev`) on every pull request. A vulnerability in a dev-only dependency is lower priority.
